# UC-8 UI QA: live and manual reproduction

These tests change Gateway configuration. Run only in a disposable, explicitly owned QA environment, never against production. The baseline UI is `12d5834d942ffab6c9718cac9cb486028c2b08f0`. Record the UI, OAM, Gateway and CLI revisions and image digests in each run. A Docker privileged Gateway shares the host kernel and requires explicit host-owner approval. Separate networks do not change that fact.

The live fault, cold-start, restart and network cases include hard-coded identifiers and paths from the 2026-10-28 isolated QA environment. They are historical reproduction cases, not portable defaults: inspect every affected spec and adapt its exact ownership guards, image and paths to a newly owned testbed before running. Do not weaken the guards on shared infrastructure. The local component tests are independent of that environment.

## Prerequisites

- Node dependencies and Playwright Chromium installed, an isolated OAM and Gateway instance, a ready Gateway store, and an OAM administrator account plus fixture accounts according to the repository E2E setup. See `e2e/CLAUDE.md` and `playwright.config.ts` for the existing setup and projects.
- The dedicated OAM instance must be named `uc8qa-gateway`. The tests deliberately skip unless this name and `UC8_QA_ALLOW_MUTATIONS=1` are supplied. The Gateway container name must begin `uc8qa-`, and the SSH host must be a simple hostname. The CLI is run inside that container.
- Connect OAM securely on loopback, for example `ssh -N -L 127.0.0.1:28080:127.0.0.1:28080 <qa-host>`. Do not publish the OAM or credentials to an untrusted network. Store test passwords in protected local files; do not commit them or include them in reports.
- Confirm Gateway `/status/ready` and the objective, API-key and netidentity store APIs return successful responses. An HTTP failure is not an empty list. Verify the instance and container belong to this campaign before running a mutation.

From the repository root, set the following using values appropriate to the isolated environment (the fixture users must already exist):

```sh
export E2E_OAM_URL=http://127.0.0.1:28080/oam
export REACT_APP_API_URL="$E2E_OAM_URL"
export E2E_ADMIN_USER='<qa-admin>'
export E2E_ADMIN_PASSWORD="$(cat /secure/path/qa-admin-password)"
export E2E_FIXTURE_PASSWORD="$(cat /secure/path/qa-fixture-password)"
export E2E_INSTANCE_NAME=uc8qa-gateway
export UC8_QA_SSH_HOST='<qa-host>'
export UC8_QA_GATEWAY_CONTAINER='<owned-uc8qa-container>'
export UC8_QA_ALLOW_MUTATIONS=1
npx playwright test e2e/tests/ai/uc8-objectives.spec.ts e2e/tests/ai/uc8-key-priority.spec.ts e2e/tests/ai/uc8-netidentity.spec.ts --project=gw --reporter=list
```

The standard Playwright project setup also reports authentication setup tests; distinguish those from the three UC-8 tests. The key test disables screenshots, video and traces because creation displays the raw key once. Keep logs and other artifacts private and inspect them for credentials before sharing. Each test uses a unique name and cleans up only its own resources; if interrupted, find and remove only the corresponding `uc8qa-` objects after verifying ownership. Do not run broad sweeps on shared instances.

## Manual checks

The steps below are a reproducible checklist corresponding to the tests, not a claim that an independent operator has already executed them. Record the UI version, instance, unique object names, results and sanitized evidence.

1. **Objective:** Open the chosen Gateway instance's Objectives page. Add a unique `uc8qa-` objective with priority `10`. Close the success dialog and check that its row shows `critical`. Run `docker exec <owned-uc8qa-container> loxicmd get objective -o json` on the QA host and compare its name and priority. Select the row, edit its priority to `-5`, save and confirm `sheddable` in the UI and `-5` in CLI. Delete the same row, then verify it is absent in both the UI and CLI. Failure to read the store is not evidence of deletion.
2. **Key:** Create a unique test objective, then open AI API Keys and add a unique test tenant and key. Expand Request Priority, choose `critical`, and set Default Objective and Allowed Objectives to the test objective. The creation dialog shows a secret once: do not copy it into evidence, screenshots, traces or logs. Dismiss the dialog, compare the key ID and fields with `loxicmd get apikey <key-id> -o json` and the Gateway API, then delete that key and objective. This proves stored configuration, not enforcement on inference requests.
3. **Network identity:** On the QA host run `docker exec <owned-uc8qa-container> loxicmd create netidentity <unique-uc8qa-name> --tenant=<unique-uc8qa-tenant> --cidr=192.0.2.0/24`. Open Network Identity in the UI and compare name, tenant and CIDR with `loxicmd get netidentity -o json`. Confirm that Add, Edit and Delete controls are absent. Delete exactly the created object with `loxicmd delete netidentity <unique-uc8qa-name>` and confirm absence in a successful CLI read. This proves visibility, not packet attribution or isolation.

For component-only priority omission and clear cases, see `e2e/local/uc8-priority/README.md`; those tests have no live Gateway. Admission rule, actual traffic, fault/recovery, compatibility and complete CLI case parity require additional tests and must not be inferred from the three cases above.

## Synthetic traffic and queue test

`uc8-traffic.spec.ts` requires an isolated synthetic receipt/hold backend and a separate Python 3 client container on the same dedicated Docker network. The fixture is `docs/assets/shared-inference/fixtures/backend.py` in the inference-gateway documentation repository. Run it with `python /fixture/backend.py` on port 8080. Supply the actual dedicated addresses and client name; the test creates and deletes its own UI rule on port 20119. Do not use a shared listener.

```sh
export E2E_GATEWAY_VIP='<gateway-address-in-dedicated-network>'
export UC8_QA_CLIENT_CONTAINER='<owned-uc8qa-client-container>'
export UC8_QA_BACKEND_IP='<synthetic-backend-address>'
npx playwright test e2e/tests/ai/uc8-traffic.spec.ts --project=gw --reporter=list
```

The first test checks an HTTP 200 and an independent, matching backend receipt. The second holds a backend request, submits one queued request and one overflow request, checks overflow 429 and zero backend receipts before release, then checks successful completion and exactly one queued receipt. These checks demonstrate the tested queue limit for this tuple; they do not establish priority scheduling or fairness. The test runs serially because the second step uses the first step's rule, and it checks the rule is absent after exact-name cleanup.

For manual reproduction, create an SSE AI rule in the UI for the dedicated Gateway VIP and synthetic backend, set admission mode `enforce`, Max Outstanding `1`, Max Queue Depth `1`, and Max Queue Wait `5000` ms. Send a JSON POST with a unique `X-Test-Nonce` and `X-Test-Hold: 1`; poll the backend `/receipt/<nonce>` until it confirms receipt. Send a second unique request while the first is held, then a third; check the third returns 429 and the backend has received neither the second nor third. Call `/release/<first-nonce>` on the backend and check the first and second complete with 200, the second has one receipt and the third has none. Delete the exact rule and confirm a successful readback no longer contains it. Preserve sanitized timestamps, response statuses and receipt counts; the fixed delay in the automation is a bounded scenario, not a general proof of scheduling.

With one request held at the backend, it waits for a sheddable request to queue, then waits for a critical request to queue, verifying both band-specific queue counts. ## Gateway store outage and recovery

These are real fault tests, not mocked responses. They affect only the explicitly named QA Gateway's network namespace, but require an approved privileged container and its own `ip` command. Do not run them on a shared or production Gateway. The OAM and PostgreSQL stay running. The tests verify the campaign label, exact container and DB addresses, an initially absent host-specific route, and register a 90-second route-restoration watchdog with a unique marker before injecting an unreachable `/32` route. The watchdog is a backup, not a substitute for checking restoration.

```sh
export UC8_QA_ALLOW_FAULTS=1
export UC8_QA_DB_IP='<the dedicated DB address, currently 172.18.0.2>'
npx playwright test e2e/tests/ai/uc8-store-recovery-refresh.spec.ts --project=gw --workers=1 --reporter=list
```

The present spec intentionally guards the exact 2026-10-28 campaign instance, Gateway name and DB IP; adapting it to another lab requires reviewing those ownership checks first. It creates an objective, proves a successful store read, isolates the Gateway from its DB, verifies the retained objective and `store_reachable=false` warning in the UI, and checks a UI create is refused with HTTP 503. On route restoration it verifies the original objective exists, the rejected objective does not, and a fresh read after the UI Refresh button reports `store_reachable=true`. It deletes its exact test objectives. Independently confirm `docker exec <owned-gateway> ip -4 route show exact <dedicated-db-ip>/32` is empty and `/status/ready` returns 200 after a run.

Manual reproduction should use the same owned lab only. Create a unique objective in the UI and verify it in a successful Gateway GET. Confirm the dedicated DB IP and that no exact host route exists in the Gateway container. Before adding `ip route add unreachable <db-ip>/32` inside that container, install the same marker-guarded 90-second watchdog used in the test. Refresh Objectives: the applied row must remain, and the UI must say the key store did not answer. Attempt a uniquely named objective and confirm HTTP 503. Delete only the unreachable route you added, remove its watchdog marker, confirm Gateway `store_reachable=true`, original objective present and rejected objective absent. Click the UI's Refresh button and confirm the warning disappears. Delete the test objective and verify readiness. Do not publish any credential or raw API response.

**Open observation UC8-STORE-RELOAD-01:** an immediate browser reload after Gateway recovery did not trigger a new objective GET within 30 seconds in one diagnostic run, while another run passed. `uc8-store-outage.spec.ts` retains this diagnostic assertion and may fail; `uc8-store-recovery-refresh.spec.ts` confirms the separate manual Refresh path. Treat both results independently and retain the RED evidence.
